# Размещение двух групп в Kubernetes

Kubernetes («кубер») запускает приложение в контейнере и управляет его перезапусками, сетью и хранилищем. Контейнер не является постоянным диском. Для этого приложения нужен отдельный постоянный том каждой группы.

Подготовлены два самостоятельных проекта: «Группа РФ» (18–24 октября) и «Группа СНГ» (24–31 октября). Исходная `secure-version` не изменена. Каждый проект содержит Dockerfile, `.dockerignore`, `deploy/kubernetes.yaml`, сервер, интерфейс и начальное наполнение. Это шаблоны для адаптации инфраструктурной командой, а не уже выполненное развёртывание.

## Обязательные параметры

В каждом `deploy/kubernetes.yaml` заменить:

- `registry.example.invalid/drakon-english:2026-09-18` или `drakon-english` — на образ в корпоративном registry; после сканирования рекомендуется закрепить digest.
- `english.example.invalid` / `english.example.invalid` — на два разных HTTPS-поддомена. В PUBLIC_ORIGIN указать точный origin без пути. Один домен с разными подпапками или портами не использовать для разделения групп: cookie не изолированы по порту.
- `REPLACE_WITH_APPROVED_CLASS` — на поддерживаемый в организации IngressClass.
- `REPLACE_WITH_INGRESS_NAMESPACE` — на namespace фактического ingress-controller. При необходимости сузить разрешение NetworkPolicy его podSelector. Шаблон рассчитан на контроллер с обычной pod-сетью; hostNetwork и SNAT требуют отдельной адаптации.
- PVC — подходящий StorageClass, объём и политику хранения. Запрошено 5 GiB; это стартовая оценка, проверить по размеру медиа. Обеспечить резервное копирование и Retain для PV по правилам организации.
Встроенные ограничения частоты входа удалены 21.09.2026 по решению владельца приложения. TRUSTED_PROXY_CIDRS больше не используется приложением. Если на Ingress есть собственные ограничения частоты, их конфигурация независима от приложения.

Убедиться, что CNI поддерживает NetworkPolicy. Политика запрещает исходящие соединения приложения и разрешает вход на 3100 только от namespace ingress. Проверить её фактическое действие: наличие YAML само по себе не доказывает изоляцию.

На Ingress настроить HTTPS с сертификатом, перенаправление HTTP на HTTPS, отсутствие кэша для ответов приложения и ограничение тела запроса до 40 MiB (это включает base64). Аннотации зависят от контроллера, поэтому не добавлены универсальным шаблоном. Не вводить сторонний публичный CDN для закрытых медиа. Запретить обход приложения прямой раздачей каталога web/assets, server/data или seed.

TLS завершается на Ingress; от него до Pod в шаблоне идёт HTTP. Если политика ИБ требует шифрования внутри кластера, инфраструктурная команда должна добавить mTLS/service mesh либо иной согласованный механизм. NetworkPolicy не шифрует трафик.

## Сборка и первый запуск

Из папки соответствующей группы (пример для РФ):

```sh
docker build -t YOUR_REGISTRY/drakon-english:2026-09-18 .
docker push YOUR_REGISTRY/drakon-english:2026-09-18
kubectl create namespace drakon-english
```

Namespace также описан в YAML; повторный apply безопасно обновит его метки. Создать отдельные Secret для пароля и TLS в каждом namespace. Пароль не хранить в Dockerfile, YAML или образе. Подготовить защищённый локальный UTF-8 файл с уникальным паролем от 12 символов без BOM; не помещать его в проект. Пример импорта существующего файла:

```sh
kubectl -n drakon-english create secret generic drakon-admin --from-file=password=/secure/path/rf-admin-password.txt
kubectl -n drakon-english create secret tls drakon-tls --cert=/secure/path/fullchain.pem --key=/secure/path/private-key.pem
kubectl apply --dry-run=server -f deploy/kubernetes.yaml
kubectl apply -f deploy/kubernetes.yaml
kubectl -n drakon-english rollout status deployment/drakon
```

Для СНГ повторить из её папки с namespace `drakon-english` и другими доменом, образом, паролем и сертификатом. Разрешить pull из закрытого registry средствами кластера (при необходимости добавить imagePullSecrets). Запрошенные 100m/128Mi и лимиты 1 CPU/512Mi являются начальными настройками, а не результатом нагрузочного теста.

Сервер запускается непривилегированным UID/GID 1000, с readOnlyRootFilesystem, без capabilities, без повышения привилегий и без service-account token. Том должен поддерживать fsGroup или быть подготовлен для UID/GID 1000. Не исправлять ошибки доступа запуском от root.

## Постоянное состояние и обновления

Один PVC монтируется в `/state` и содержит:

- `/state/data` — программа, участники, задания, контакты, дома, отметки жребия, хеш пароля, приглашения и сессии.
- `/state/assets` — закрытые изображения и аудио, в том числе загруженные в админке.

При первом запуске данные копируются из `server/seed`, медиа — из образа. При повторном запуске существующие данные и одноимённые медиа НЕ перезаписываются. Обновление seed в новом образе не меняет уже заполненный PVC: менять контент через админку или выполнять контролируемую миграцию при остановленном процессе. Не удалять PVC ради обновления программы.

Для каждой группы **replicas: 1, strategy: Recreate**, без HPA и без второго процесса, пишущего в тот же том. Файловые очереди записи защищают только один процесс. ReadWriteOnce не запрещает два Pod на одном узле. Не запускать дубли вручную; для более строгой защиты использовать ReadWriteOncePod, если CSI поддерживает этот режим. Обновление может вызвать короткий перерыв в онлайне.

Проверка `/api/info` используется для startup/liveness и подтверждает работу HTTP-процесса. Отдельная `/api/ready` используется для readiness: проверяет структуру пяти файлов контента, конфигурацию пароля, имеющиеся файлы приглашений/сессий/жребия, а также создание, переименование, чтение и удаление временного файла в каталогах данных и медиа. Возвращает только `{ready:true}` (200) или `{ready:false}` (503), без данных участников и причин отказа. Проверка не восстанавливает повреждённые данные, не сканирует все медиа и не заменяет backup и мониторинг. Мониторить 5xx, 401, место на диске, перезапуски, сертификаты и backup; не записывать секреты и персональные ответы в логи.

Пароль из Secret применяется только при первом запуске, если в config.json ещё нет пароля. Для ротации: обновить Secret, дождаться обновления смонтированного файла и выполнить в Pod:

```sh
kubectl -n drakon-english exec deployment/drakon -- node server/server.js --password-file /run/secrets/drakon/password
```

Эта операция завершает прежние сессии организатора. Простой rollout с новым Secret существующий пароль не меняет.

## Резервное копирование и восстановление

Копировать весь `/state`, а не только JSON. Для согласованной файловой копии остановить приложение (`replicas: 0`) либо использовать проверенный согласованный snapshot тома; выполнить копирование и вернуть одну реплику. Операцию и сроки хранения согласовать с владельцем сервиса. Проверять восстановление в отдельном namespace, не на рабочем томе.

Восстановление invitations/config/sessions восстанавливает и связанные доступы. При инциденте нельзя бездумно возвращать старый snapshot: он может вернуть отозванные приглашения. После восстановления выполнить нужные отзывы и ротации. Данные и backup не зашифрованы самим приложением; шифрование томов и backup обеспечивает инфраструктура.

## Приёмка перед рассылкой

1. Без входа `/api/content`, `/participants.json` и известный URL закрытого медиа возвращают отказ; виден только экран входа.
2. Администратор каждой группы входит своим паролем. Нет чужих участников и неверных дат.
3. Ссылка РФ не работает на домене СНГ и наоборот. Ротация отзывает старую ссылку и сессию онлайн.
4. Перезапуск Pod сохраняет изменения, приглашения, загруженный файл и доступ участника. Это обязательно проверить на реальном PVC.
5. Нельзя войти с поддельным Origin. Участник не может изменять программу или дома других людей.
6. Проверить массовый вход через общий Wi-Fi: приложение не ограничивает число попыток входа; проверить также независимую конфигурацию Ingress.
7. На Android и iPhone проверить браузер и установку на главный экран, вход по ссылке и коду, загрузку медиа, жребий офлайн, синхронизацию, выход и отзыв.
8. Удалить примеры участников СНГ, заменить тестовые контакты и аудио. Для РФ заполнить участников, контакты, задания и назначения домов.

Docker и kubectl отсутствуют в среде подготовки. Локально проверены сервер, браузерные сценарии, сохранение медиа и состояния при повторной инициализации; сборка образов, admission, CSI, Ingress и NetworkPolicy в вашем кластере ещё не проверялись.
